# Спецификация приложения «Запись на звонок»

**Статус**: утверждена · 24.10.2026 · ревизия a010c575664643f656fe69981f6151c62648e7d6
**Охват**: внешнее поведение системы — роли, сценарии, логические данные и ограничения бронирования. Стек, архитектура и контракт API в спецификацию не входят.
**Источник требований**: задание Хекслета «Запись на звонок» и принятые решения из `docs/adr/`.
**Правило утверждения**: содержательная правка нормативных разделов возвращает документ в статус «на утверждении», косметическая — нет. Утверждение привязано к ревизии: после мержа PR шапка принимает вид `**Статус**: утверждена · <дата> · ревизия <sha последнего содержательного коммита>`.

## 1. Роли

В системе две роли. Регистрации, входа и авторизации нет: роли не хранятся и не аутентифицируются, разделение между ними только навигационное — административная часть и список предстоящих встреч доступны любому посетителю (см. § 9).

- **Владелец календаря** — роль в интерфейсе, отдельного профиля с учётными данными у неё нет. Создаёт и ведёт типы событий, просматривает предстоящие встречи.
- **Гость** — посетитель без аккаунта и без входа. Выбирает тип события, слот и создаёт запись.

## 2. Логические данные

### Тип события

| Поле | Тип | Обязательность | Изменяемость |
| --- | --- | --- | --- |
| `id` | целое, генерирует система | — | неизменяем |
| Название | строка | да | редактируется |
| Описание | строка | нет | редактируется |
| Длительность | целое число минут | да | задаётся при создании, далее не меняется |

Удаление типа события — **мягкое (soft-delete)**: тип перестаёт показываться гостям и пропадает из списка административной части, существующие записи сохраняются и остаются видимыми владельцу. Удалённый тип не редактируется и не восстанавливается через интерфейс: после удаления управление им завершено. Обоснование — [ADR 0001](adr/0001-soft-delete-event-types.md).

### Запись

| Поле | Тип | Обязательность |
| --- | --- | --- |
| Тип события | ссылка на тип события | да |
| Начало | дата и время | да |
| Имя гостя | строка | да |
| Email гостя | строка, проверяется формат | да |
| Комментарий | строка | нет |

Запись всегда целиком принадлежит одному типу события и одному слоту.

## 3. Сценарий гостя

1. Гость открывает страницу со списком типов событий: для каждого видны название, описание (если задано) и длительность.
2. Выбирает тип события и открывает календарь.
3. В календаре доступны даты в пределах окна записи (см. § 5).
4. Выбрав дату, гость видит только свободные слоты этой даты для выбранного типа события; занятые слоты в списке не показываются вовсе.
5. Заполняет имя и email (комментарий — по желанию) и создаёт запись.
6. После успешного создания гость видит подтверждение с деталями: тип события, дата и время начала, длительность, введённые данные.

## 4. Сценарии владельца

### Создание типа события

Владелец задаёт обязательные название и длительность в минутах; описание необязательно. Идентификатор назначает система. Попытки создать тип с пустым названием или некорректной длительностью отклоняются.

### Ведение типов событий

Владелец может изменить название и описание любого активного типа события (включая seed) и мягко удалить его. Удалённый тип после этого не редактируется и не восстанавливается через интерфейс.

### Предстоящие встречи

Одна страница показывает записи **всех** типов событий в едином списке. Поля строки: дата и время начала, тип события (название и длительность), имя и email гостя, комментарий (если есть). Список отсортирован по времени начала по возрастанию, фильтров нет. Предстоящей считается запись, начало которой ещё не наступило; идущая встреча предстоящей не считается и скрыта вместе с прошедшими. Записи мягко удалённых типов событий остаются видимыми.

## 5. Слоты, окно записи и время

- Сетка старта слотов — каждые **30 минут**, независимо от длительности типа события.
- Рабочее окно дня — **09:00–18:00**.
- Запись должна целиком укладываться в рабочее окно: `конец = начало + длительность ≤ 18:00`. Если длительность типа события больше рабочего окна, у этого типа нет доступных слотов.
- Окно записи — **14 календарных дней, начиная с текущей даты включительно** (сегодня и следующие 13 дней). За его пределами слоты недоступны.
- Слоты раньше текущего момента недоступны (для сегодняшнего дня — только будущее время).
- Время ведётся в **одном фиксированном поясе — Europe/Moscow**, без конвертаций между зонами и без подстройки под пояс браузера. «Текущая дата и время» — по этому поясу.

## 6. Правило занятости

На одно и то же время нельзя создать две записи, даже если это разные типы событий.

Занятость определяется **пересечением интервалов**: запись занимает `[начало, начало + длительность)`, и новая запись запрещена, если её интервал пересекается с интервалом любой существующей записи. Совпадение начала не обязательно.

Проверка выполняется на сервере; от одновременных запросов дополнительно защищает гарантия на уровне хранилища (уникальность/транзакция), чтобы исключить двойную запись при гонке.

Существующие записи не пересчитываются: они остаются в силе, видны владельцу и занимают свой интервал, даже если их старт не лежит на текущей сетке.

## 7. Seed-данные

При первом запуске система содержит два типа события с длительностями **15** и **30** минут. Названия и описания задаются в рамках реализации и правятся владельцем как обычные типы.

## 8. Страницы и маршруты

- `/` — лендинг (существует, не переписывается).
- `/book` — список типов событий для гостя.
- `/book/:id` — календарь, свободные слоты и форма записи для выбранного типа события.
- `/events` — предстоящие встречи (взгляд владельца).
- `/admin` — административная часть владельца: создание и ведение типов событий.

Маршрут `:id` использует системный целочисленный идентификатор типа события.

## 9. Вне рамок

Сознательно исключено из текущей версии:

- отмена и перенос записи;
- email- и любые другие уведомления;
- регистрация, вход, авторизация, роли-множества;
- интеграции с внешними календарями;
- повторяющиеся события;
- часовые пояса и конвертации между зонами.

## 10. Оставлено на усмотрение реализации

Спецификация намеренно не фиксирует внутренние детали: точные правила валидации строк (длина, формат email сверх «проверяется»), детали защиты от гонок на уровне хранилища, оформление и внутреннюю структуру кода, а также детали интерфейса — счётчики свободных слотов, показ времени создания записи и кнопку «Забронировать ещё».

Уже принятые решения здесь не пересматриваются, а зафиксированы в ADR:

- мягкое удаление типов событий — [ADR 0001](adr/0001-soft-delete-event-types.md);
- гарантия отсутствия пересечений записей на уровне хранилища — [ADR 0002](adr/0002-booking-overlap-guarantee.md);
- фиксированный пояс записи — [ADR 0003](adr/0003-fixed-booking-timezone.md).
